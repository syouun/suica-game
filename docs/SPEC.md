# フルーツドロップ 仕様書 v1.5（iPhone でしばらくすると BGM が止まる不具合を修正）

物理落ち物パズル「スイカゲーム」のゲーム性・操作感・演出の流れを再現した、オリジナルデザインのWebブラウザゲーム「フルーツドロップ」の仕様書。
実装は `index.html` 1ファイル。自己チェック用のテストは `tests/selfcheck.js`。

- 「15. 確認事項」は承認時の回答を反映済み。
- v1.0 からの変更点とその理由は、末尾の「16. 変更履歴」にまとめた（v1.2 の改修内容を含む）。
- `index.html` は外部への通信を一切行わない。インターネットに接続していないPCでも、ファイルをダブルクリック（`file://`）するだけで動く。

## 1. 用語・座標系・単位

| 用語 | 定義 |
|---|---|
| u（ユニット） | 論理座標の長さの単位。**コンテナ内幅 = 400u** |
| 論理座標系 | 原点 = コンテナ内側の左上（縁の高さ）。x は右向きが正、y は下向きが正 |
| ステップ | 物理演算の1回分。**1ステップ = 1/60秒 = 16.667ms**（固定） |
| ゲーム時間 | 物理ステップを積み上げた時間（ms）。投下クールダウン・ゲームオーバー判定はこの時間で測る |
| 実時間 | `requestAnimationFrame` のタイムスタンプ差分。描画エフェクトのアニメーションに使う |
| s（表示倍率） | 1u を何CSSピクセルで描くか。画面サイズから毎回計算する |
| r | 果物の見た目上の半径（u） |

- 速度は仕様書では **u/秒** で書く。Matter.js 0.19 の `body.velocity` は「1ステップあたりの移動量（u/step）」なので、**u/step = u/秒 ÷ 60** で変換する。
- 角速度も仕様書では rad/秒で書き、Matter.js に渡すときは ÷60 して rad/step にする。

## 3. 画面レイアウト（論理座標）

### 3-1. ゲームフィールドの寸法

| 要素 | 値（u） | 備考 |
|---|---|---|
| コンテナ内幅 W | 400 | x = 0〜400 |
| コンテナ内高 H | 500 | y = 0（縁）〜500（床）。**幅1：高さ1.25** |
| 枠の太さ（見た目）T | 16 | 左右の壁・床の見た目の厚さ |
| 枠の外寸 | 432 × 516 | x = −16〜416、y = −4〜516（縁の上の丸いキャップ分を含む） |
| デッドライン Y_DEAD | 40 | 縁から 40u 下（内高の8%）。→確認事項 Q3 |
| 投下待ち果物の中心 Y_DROP | −60 | 縁より上。最大の投下果物（段階5, r=34）でも下端が −26 で縁より上 |
| 描画範囲（ビューポート） | x = −30〜430（幅460）、y = −130〜530（高さ660） | この範囲が画面に収まるよう s を決める |

### 3-2. 画面の分割

- **横長（`innerWidth / innerHeight ≥ 0.9`）**：3列。`[左パネル 200px] [ゲームフィールド] [右パネル 200px]`
  - 左パネル：タイトル、スコア、ハイスコア
  - 右パネル：NEXT、進化の輪、操作ボタン（一時停止とミュートを横に並べる）
- **縦長（< 0.9）**：3行。`[上バー 76px] [ゲームフィールド] [下バー 112px]`
  - 上バー：スコア／ハイスコア／NEXT（3つのカードを横に並べる）
  - 下バー：タイトル／進化の輪（直径 100px）／操作ボタン（一時停止とミュートを縦に並べる）
- パネル幅・バーの高さは、画面が狭いときは `clamp()` で縮める（横長：`clamp(140px, 18vw, 220px)`）。
- ゲームフィールドの倍率：`s = min(使える幅 / 460, 使える高さ / 660)`。フィールドは使える領域の中央に置く。

## 4. 果物の進化表

半径は内幅に対する比率 `ratio` で持ち、`r = ratio × 400` で求める。要件の目安値はそのまま採用する（大小の順序と段階差が十分なため。半径は段階ごとに約1.2倍ずつ大きくなる）。

| 段階 | id | 名前 | ratio | r(u) | 基本色 | 生成時の得点 | 出現の重み |
|---|---|---|---|---|---|---|---|
| 1 | cherry | さくらんぼ | 0.030 | 12 | `#E8394A` | 1 | 30 |
| 2 | strawberry | いちご | 0.0425 | 17 | `#F2545B` | 3 | 25 |
| 3 | grape | ぶどう | 0.0575 | 23 | `#8E5CC8` | 6 | 20 |
| 4 | dekopon | デコポン | 0.0675 | 27 | `#F7A23B` | 10 | 15 |
| 5 | kaki | かき | 0.085 | 34 | `#F07F2A` | 15 | 10 |
| 6 | apple | りんご | 0.105 | 42 | `#E53935` | 21 | − |
| 7 | pear | なし | 0.125 | 50 | `#D8CC5C` | 28 | − |
| 8 | peach | もも | 0.150 | 60 | `#FFB3C1` | 36 | − |
| 9 | pineapple | パイナップル | 0.180 | 72 | `#F9D046` | 45 | − |
| 10 | melon | メロン | 0.215 | 86 | `#B5DB6B` | 55 | − |
| 11 | watermelon | スイカ | 0.255 | 102 | `#4FAE4A` | 66 | − |

- **得点**：合体で生まれた果物の「生成時の得点」を加算する。例：さくらんぼ×2 → いちご誕生 → +3。
- **スイカ同士の合体**：両方消えて **+66**。生まれる果物はない。
  - 妥当性：スイカ2個がそろうのは非常にまれで、達成のご褒美として、得点と「コンテナに大きな空きができる」ことの両方が得られる。スイカ誕生と同等以上の演出（6-6）を出す。得点を 66 にする根拠は「最上位段階の得点を1回分もらう」という、ほかの段階と同じ決まりで説明できること。→確認事項 Q1
- **出現の重み**：段階1〜5を重み 30:25:20:15:10（%）で抽選する。小さい果物を多めにして、序盤の連鎖を作りやすくする。→確認事項 Q2
- 開始時に「現在の果物」と「NEXT」を両方抽選する。投下すると NEXT が現在の果物になり、新しい NEXT を抽選する。

### 5-2. コンテナ（木箱風）

オフスクリーンCanvasに「内側の層」と「枠の層」の2枚を、画面サイズが変わるたびに描き直してキャッシュする。

**内側の層**（果物の後ろに描く）
1. x = 0〜400、y = −4〜500 を、下の角だけ半径10uの角丸にした四角形で `#FFF8E8` に塗る。
2. 内側の影：左右の端から 14u、床から 14u の範囲に、`rgba(110,70,30,0.14)` → 透明の線形グラデーションを重ねる。
3. 床の少し上（y = 470〜500）に、`rgba(110,70,30,0.05)` の帯を重ねて奥行きを出す。

**枠の層**（果物の手前に描く）
1. 枠のU字形：外側（x = −16〜416、y = −4〜516、外の下角は半径30u）から、内側（x = 0〜400、y = −∞〜500、内の下角は半径10u）を `evenodd` で抜いた形。
2. 形の後ろに、同じ形を (0, +6u) ずらして `rgba(110,70,30,0.18)` で塗った影を置く（ぼかしなしの、ずらした影）。
3. 塗り：上から下へ `#F0C27B` → `#E2A95E` の線形グラデーション。
4. 木目：左右の壁には縦線、床には横線を各3本。`rgba(122,78,38,0.15)`、太さ 1.5u。線は少し揺らした2次ベジェ曲線（揺らし方はシード付き乱数で固定）。
5. 内側のふちのハイライト：内側の輪郭から 3u 内側に `#FADDA8`、太さ 2u。
6. 外側の輪郭線：`#7A4E26`、太さ 3u、線の角は丸く。
7. 壁の上端（y = −4）には、半径 8u の半円のキャップをつけて丸く見せる。

※ 物理上の壁（9-6）は見た目の枠よりずっと厚く、縁より上にも続いている。

### 5-3. 果物の描画ルール（全種共通）

| 項目 | 値・手順 |
|---|---|
| 輪郭線の太さ | `lw = 2 + 0.05 × r`（u）。r=12 → 2.6u、r=102 → 7.1u。色 `#5A3A22`、`lineJoin = lineCap = "round"` |
| 塗り | 単色のフラット塗り（もものみ、ゆるいグラデーション） |
| ハイライト | 中心 (−0.42r, −0.45r)、横半径 0.22r、縦半径 0.13r、−40°回転の楕円。白、不透明度 0.75 |
| 顔の位置 | 中心から (0, +0.08r) を顔の基準点にする |
| 目 | 基準点から ±0.30r 横、−0.02r の位置。点の目は半径 `max(1.3, 0.07r)` |
| 口 | 基準点から +0.20r の位置。幅 0.18r。線の太さ `max(1.2, 0.045r)` |
| 頬 | 基準点から ±0.48r 横、+0.16r の位置。横半径 0.13r、縦半径 0.08r の楕円 |
| 回転 | 物理ボディの `angle` で、顔・模様・飾りも含めて丸ごと回転させる |
| はみ出し | ヘタ・葉・冠などの飾りは、円の外へ最大 0.45r まではみ出してよい（見た目だけ。当たり判定は円） |

**描く順序**（1枚のスプライト内）
1. 後ろの飾り（冠・軸・葉など、本体の後ろに来るもの）を、輪郭 → 塗りの順に描く
2. 本体のシルエット（円、またはデコポンのような合成形）を、`2 × lw` の太さで輪郭色に塗る（ふち取り）
3. 本体を基本色で塗る（2の線の内側半分が隠れて、外側に `lw` 分だけ輪郭が残る）
4. 模様：本体の形でクリップして描く
5. ハイライト
6. 顔（目 → 口 → 頬）
7. 手前の飾り

（2→3 の「ふち取りしてから塗る」方式で、合成形でも内側に線が残らないようにする。）

**スプライトのキャッシュ**
- 段階ごとに、オフスクリーンCanvasへ事前に描いておく。
- 1辺のピクセル数：`ceil(2 × (1.45r + lw) × s × dpr)`。描画倍率 `s × dpr` には上限 4 を設けて、メモリを抑える。
- 画面サイズや dpr が変わったら作り直す（作り直すまでの間は古いキャッシュを拡大縮小して使う）。
- 灰色版（ゲームオーバー用）は、ゲームオーバーになったときに、カラー版の画素を輝度 `Y = 0.299R + 0.587G + 0.114B` に変換して作る。暗幕の上で見えるよう、明るさは `70 + 0.62Y` に持ち上げる。`ctx.filter` は Safari の対応が不安定なので使わない。
- 描画時：`translate(x, y)` → `rotate(angle)` → `scale(見た目の倍率)` → `drawImage`（論理サイズで描く）。`imageSmoothingQuality = "high"`。

**模様のランダム配置**は、段階ごとにシード付き乱数（mulberry32、シード = 段階 × 1000 + 7）で決めて固定する。

### 5-7. NEXT と進化の輪

- **NEXT**：小さな Canvas に、次の果物を「段階5が枠の直径の80%になる倍率」で描く（段階ごとの大きさの違いが分かる）。NEXT が変わったときに、0.6 → 1.0倍、200ms、easeOutBack（c1 = 1.70158）で登場させる。
- **進化の輪**：Canvas の中心を基準に、半径 = Canvas 幅 × 0.36 の円周上に、11種を真上（さくらんぼ）から時計回りに等間隔（32.7°ごと）で並べる。各果物の表示半径 = Canvas 幅 × (0.045 + 0.050 × (段階 − 1) / 10)。後ろに円周の線（`rgba(138,90,43,0.25)`、太さ 2px）と、時計回りを示す小さな三角の矢印を3つ描く。
- 進化の輪のうち、そのゲームでまだ作っていない段階（段階6以上）は不透明度 0.35 で描き、作れたら 1.0 にする（いまの到達状況が分かるようにする）。

## 6. エフェクト仕様

### 6-0. 共通

- エフェクトの時間は **実時間**（rAF の差分。1フレーム最大 50ms に制限）で進める。タブが非表示の間はループごと止まる。
- イージング関数の定義（t は 0〜1）：
  - `easeOutCubic(t) = 1 − (1 − t)³`
  - `easeOutQuad(t) = 1 − (1 − t)²`
  - `easeInOutQuad(t) = t < 0.5 ? 2t² : 1 − (−2t + 2)² / 2`
  - `easeOutBack(t, c1) = 1 + (c1 + 1)(t − 1)³ + c1(t − 1)²`
- エフェクトのオブジェクトは配列で管理し、寿命が来たら取り除く。パーティクルは同時に最大 400 個まで（超えた分は古いものから消す）。

### 6-1. 合体：新しい果物の登場

| 項目 | 値 |
|---|---|
| 出現位置 | 消えた2個の中心の中点。ただし `x` は [r, 400 − r]、`y` は 500 − r 以下に収める（新しい果物が壁や床に食い込まないように） |
| 見た目の倍率 | `scale(t) = 0.6 + 0.4 × easeOutBack(t, c1 = 4.0)`、所要時間 **250ms** |
| 倍率の推移 | t = 0 で 0.60倍 → t ≈ 0.47（117ms）で最大 **1.15倍** → t = 1 で 1.00倍 |
| c1 = 4.0 の根拠 | easeOutBack の最大値は `1 + 4c1³ / (27(c1+1)²)`。1.15倍にするには最大値 1.375 が必要で、c1 = 4.0 のとき 1.3756 になる |
| 物理ボディ | 最初から正規サイズ。見た目の倍率は描画にだけ使う |
| 初速 | 元の2個の速度の平均（9-7） |

### 6-2. 果汁パーティクル

| 項目 | 値（新しく生まれた果物の段階を n、半径を R とする） |
|---|---|
| 数 | `6 + 2n` 個（n = 2 で 10個、n = 11 で 28個）。スイカ誕生時は3倍 |
| 形 | 塗りつぶした円（輪郭なし） |
| 色 | 生まれた果物の基本色と、それを白へ 35% 寄せた色を半々 |
| 初期半径 | `random(2.0, 3.5) + 0.04R`（u） |
| 初期位置 | 合体地点から、半径 0.5R の円周上のランダムな点 |
| 初速 | 中心から外向き。速さ `random(140, 280) + 2R` u/秒。上向きに 80 u/秒を足す |
| 重力 | 900 u/秒²（下向き） |
| 空気抵抗 | 毎秒、速度に 0.90 を掛ける（`v *= 0.90^dt秒`） |
| 寿命 | `random(450, 700)` ms |
| 消え方 | 半径は寿命いっぱいかけて 1.0 → 0.5倍に線形で縮む。不透明度は寿命の 40% までは 1、そこから 0 まで easeOutQuad で下げる |

### 6-3. 得点ポップアップ

| 項目 | 値 |
|---|---|
| 文字 | `+点数`（例：`+21`） |
| 位置 | 合体地点。所要時間 800ms で、上へ 40u 移動（easeOutCubic） |
| 大きさ | 文字サイズ `16 + 1.4n` u（n は段階）。最初の 120ms で 0.5 → 1.0倍（easeOutBack, c1 = 1.70158） |
| 色 | 塗り `#FFFFFF`、ふち `#5A3A22` 太さ 4u（`strokeText` を先に描いてから `fillText`） |
| 消え方 | 0〜300ms は不透明度 1、300〜800ms で 1 → 0（easeInOutQuad） |
| 回転 | 果物が回転していても、ポップアップは回転させない |

### 6-4. リング波紋

| 項目 | 値 |
|---|---|
| 形 | 白い円の輪（`#FFFFFF`） |
| 半径 | 0.9R → 1.8R、所要時間 350ms、easeOutCubic |
| 線の太さ | 6u → 0u（線形） |
| 不透明度 | 0.9 → 0（easeOutQuad） |

### 6-5. 画面揺れ（共通の仕組み）

- 揺れの量 `A(t) = A0 × (1 − t/D)²`（D は継続時間）。
- 毎フレームのずれ = (A·sin(2π·f·t), A·cos(2π·f·t·1.3)) u、f = 28Hz。
- 複数の揺れが重なったときは、大きいほうを採用する。

### 6-6. スイカ誕生時の特別演出

スイカが生まれたとき（段階10同士の合体）と、スイカ同士が合体して消えたときに出す。

| 項目 | 値 |
|---|---|
| 画面揺れ | A0 = 8u、D = 500ms |
| 果汁パーティクル | 通常の3倍（28 × 3 = 84個）。初速は 1.3倍 |
| 紙吹雪 | 24枚。4u × 7u の長方形、色は `#FF6F91` `#FFC94A` `#6FD08C` `#5BC0EB` `#B28DFF` から無作為に選ぶ。初速は上向き中心の ±60° に 300〜520 u/秒。重力 600 u/秒²、ひらひらと回転（角速度 ±8 rad/秒）、寿命 1200ms、最後の 400ms でフェードアウト |
| リング波紋 | 2重。2本目は 120ms 遅らせ、半径は 0.9R → 2.4R |

| 得点ポップアップ | 文字サイズ 1.5倍、所要時間 1100ms |
| 効果音 | スイカ誕生音（7章） |

### 6-7. 着地の砂ぼこり

| 項目 | 値 |
|---|---|
| 発生条件 | `collisionStart` で、接触法線方向の相対速度 > **600 u/秒** のとき（相手は床・壁・果物のどれでもよい）。同じ果物では 300ms に1回まで |
| 位置 | 接触点（`pair.collision.supports` の平均） |
| 数 | 4個（相対速度が 900 u/秒を超えたら 6個） |

| 寿命・不透明度 | 300ms、0.5 → 0（線形） |

### 6-8. ゲームオーバー演出

ゲームオーバーになった時点を t = 0 とする。物理演算はこの時点で止める（→確認事項 Q7）。

| 時刻 | 内容 |
|---|---|
| 0ms | 入力を無効にする。ゲームオーバー音を鳴らす。デッドラインは赤のまま点灯（点滅は止める） |
| 0〜500ms | フィールド全体に暗幕 `rgba(40,25,15, α)` を重ねる。α は 0 → 0.45（easeOutQuad） |
| 300ms〜 | 果物を **上から順に**（y が小さい順）灰色にする。1個ごとの間隔 `min(60ms, 1500ms / 個数)`。各果物は 200ms かけて、カラー版から灰色版へ切り替える（灰色版を不透明度 0 → 1 で上に重ねる） |
| 最後の果物の灰色化が終わってから 300ms 後 | 結果パネルが下から現れる：`translateY(40px)`・不透明度 0 → `translateY(0)`・不透明度 1、450ms、`cubic-bezier(0.34, 1.56, 0.64, 1)`（easeOutBack 相当） |
| パネル表示後 | 「もう一度」ボタンにフォーカスを当てる。Enter / Space でもリトライできる |

- 灰色の果物は、暗幕の **上** に描く（暗くなった画面で、灰色の果物が浮かび上がる）。
- ハイスコアを更新したら、パネルに「NEW RECORD!」バッジを出し、0.9 → 1.1 → 1.0倍で弾ませる（400ms）。

### 6-9. スコア表示のカウントアップ

| 項目 | 値 |
|---|---|
| アニメーション | 表示中の値から新しい値まで 400ms で増やす（easeOutCubic）。途中で加算があったら、その時点の表示値から新しい目標値へ、あらためて 400ms |
| 数字の弾み | 加算のたびに、スコアの数字を 1.15 → 1.0倍、150ms（CSS transition） |
| ハイスコア | スコアがハイスコアを超えたら、その場でハイスコアの表示も更新する（localStorage への保存はゲームオーバー時と、ページを閉じるとき `pagehide`） |

## 7. 効果音仕様

- `AudioContext` は、最初の `pointerdown` / `keydown` のとき（スタート画面の「GAME START」ボタン、または Space / Enter キーを含む）に作成または `resume()` する。それまでは一切鳴らさない。
- 出力の構成：効果音 → マスターゲイン（0.6）→ `DynamicsCompressor`（threshold −18dB, ratio 4）→ 出力。BGM（7-2）は BGMバス → 同じマスターゲインにつなぐ。
- ミュート：マスターゲインを 30ms かけて 0 にする。BGMと効果音の両方がまとめて消音される。設定は localStorage `fruitdrop.muted` に保存する。キーボードの M でも切り替える。
- タブが非表示になったら `AudioContext.suspend()`、表示に戻ったら `resume()` する（BGMの時計も止まる）。
- エンベロープの記法：A = 立ち上がり、D = 減衰（指数カーブで 0.0001 まで下げる）。

| 音 | 合成方法 |
|---|---|
| 投下「ぽとっ」 | sine、周波数 520Hz → 300Hz（90ms、指数カーブ）、ゲイン 0.25、A 5ms・D 110ms |
| 合体「ぷちゅん」 | ① triangle、基本周波数 `f = 300 × 1.12^(n−1)`（n は生まれた段階）、f → 1.6f へ 80ms で上げる、ゲイン 0.22、A 4ms・D 180ms。② ホワイトノイズを bandpass（中心 2000Hz、Q 1.2）に通す、ゲイン 0.08、D 40ms。合体の音は 40ms に1回までにする（連鎖で音が重なりすぎないように） |
| スイカ誕生「きらりん」 | triangle で 523 / 659 / 784 / 1047Hz を 90ms 間隔で順に鳴らす（各ゲイン 0.18、A 5ms・D 260ms）。同時に sine で 2093Hz を 4本、±6 cent ずらして重ねたきらめき音（ゲイン 0.04、D 600ms） |
| ゲームオーバー | triangle で 392 → 330 → 262Hz を 220ms 間隔で順に鳴らす（ゲイン 0.2、D 260ms。最後の音だけ D 700ms）。最後の音に 5Hz・±8 cent のビブラート |

着地音は要件にないため付けない（→確認事項 Q8）。

### 7-2. BGM（Web Audio によるループ演奏）

外部の音声ファイルを使わず、プログラムで合成した曲をループ再生する。

| 項目 | 値 |
|---|---|
| 曲調 | 明るく穏やかなマリンバ＋トイピアノ風。ハ長調、**96 BPM**、4/4拍子、8小節（約20秒）のループ |
| コード進行 | C → Am → F → G → C → Em → F → G（1小節に1コード） |
| 譜面の単位 | 8分音符（1小節8ステップ、全64ステップ） |
| メロディ | マリンバ風：sine の基音（ゲイン 0.13、A 4ms・D 550ms）＋ 2倍音の triangle（ゲイン ×0.18、D 220ms。スマホの小さなスピーカーでも輪郭が聞こえるように）＋ 3.93倍音の sine（ゲイン ×0.3、D 100ms）。音域は A4〜C6 |
| ベース | triangle。スマホのスピーカーは 150Hz 以下をほとんど鳴らせないので、1オクターブ上（E3〜C4）で鳴らす。各小節の1拍目に根音（ゲイン 0.10、D 500ms）、3拍目に5度上（ゲイン 0.08、D 450ms） |
| 伴奏 | トイピアノ風：triangle の基音（ゲイン 0.06、D 380ms）＋ 2倍音の sine（ゲイン ×0.3、D 140ms）。2拍目と4拍目の頭で、コードの2音を同時に鳴らす |
| シェイカー | ホワイトノイズを highpass（6500Hz）に通し、裏拍（8分の裏）にゲイン 0.03・D 35ms で刻む |
| 音量 | BGMバスのゲイン 1.0。出力での実効ゲイン（マスター 0.6 × バス × 各音）は、メロディ 0.078、伴奏 1音 0.036、ベース 0.06。効果音のピーク（約 0.15）より約 6dB 小さく、スマホの内蔵スピーカーでもはっきり聞こえる。実測（2.5秒間、マスター出力）はピーク 0.145、RMS 0.017。音量の値は `BGM.LEVEL` と `BGM.GAIN` にまとめてある |
| 鳴り始め | 「GAME START」を押したユーザー操作の中で `AudioContext.resume()` を呼び、iOS 向けに無音の1サンプルを再生して解禁する。ループのデータは起動時に書き出し済みなので、BGM はクリックから約 0.02秒後に鳴り始める（書き出しが終わっていなければ、終わった瞬間に始める）。フェードインは 0.12秒だけ |
| 再生方式 | 起動時に、8小節ぶん（20秒＋余韻1秒）を `OfflineAudioContext`（44.1kHz・モノラル）で一度だけ音声データに書き出す（ユーザー操作は不要）。ループ終わりで鳴り始めた音の余韻1秒は、データの先頭に足し込んで、継ぎ目でも音が切れないようにする。再生は `AudioBufferSourceNode` 1つを `loop = true`（`loopEnd` = 20秒）で鳴らすだけで、再生中にタイマーも音ごとのノードも使わない |
| 見張り | 毎フレーム、BGM が鳴っているはずなのに再生ノードがなくなっていたら（iOS が止めた場合など）、その場で鳴らし直す。`AudioContext` が iOS の `interrupted` 状態になったら再開を試み、画面への復帰（`pageshow`・`focus`・`visibilitychange`）や、次のタップでも再開する |
| 再生開始 | スタート画面で「GAME START」（または Space / Enter）を押したとき。リトライ時は最初から |
| 一時停止中 | BGMは止めずに、0.25秒かけて音量を 35% に下げる。再開すると元に戻す |
| ゲームオーバー | 1.2秒かけてフェードアウトして止める（ゲームオーバーの効果音と重ならないように） |
| ミュート | マスターゲインが 0 になるので、BGMも消える（再生は続けるので、ミュートを解除するとすぐ聞こえる） |

```
                                                         ▲  │ ⇅ 一時停止（Game.paused）                                    │
                                                         │  │ ⇅ 手動 ⇄ AUTO（Game.auto）                                   │
                                                         └──┴───────────────────────「もう一度」─────────────────────────────┘
```

- PLAYING の中に、「一時停止しているか」（8-7）と「AUTOか手動か」（8-8）の2つのフラグがある。
- タブが非表示の間は、どの状態でもループそのものを止める（10-4。一時停止フラグとは別）。

### 8-2. 投下

| 項目 | 仕様 |
|---|---|
| 位置の決め方 | マウスの移動／タッチのドラッグ／←→キー。マウスとタッチは指している x 座標にそのまま追従する。←→キーは押している間 360 u/秒で動く |
| 投下の操作 | 左クリックのボタンを離したとき／指を離したとき／Space キー（押しっぱなしの連打は無視する） |
| 範囲の制限 | x を [r + 1, 400 − r − 1] に収める（r は投下する果物の半径） |
| 投下 | (x, −60) に物理ボディを作り、初速 0・角速度 0・角度 0 で放す。**待機中はボディを作らない**ので重力の影響を受けない |
| クールダウン | 投下から **500ms**（ゲーム時間）たつまで、次を装填しない。この間の投下操作は無視する（予約しない） |
| 操作の範囲 | ポインター操作は、ゲームフィールドの要素の上で始まったものだけを受け付ける（UIボタンの操作では投下しない） |

### 8-3. 合体

1. 物理エンジンの `collisionStart` と `collisionActive` の両方で、果物同士のペアを調べる。
2. 次の条件をすべて満たすペアを **合体キュー** に積み、その場で両方に `merging = true` を立てる：同じ段階／どちらも `merging` が false／どちらも取り除かれていない。
   - その場でフラグを立てるので、3個が同時に触れていても、最初に見つかった1組だけが合体する。残りの1個は次のステップ以降に、別の相手と改めて判定される。
3. `Engine.update` が終わってから、キューを順番に処理する：
   - 両方がまだワールドにあるか確かめる（念のため）。
   - 両方のボディをワールドから取り除き、果物の一覧からも消す。
   - 段階 ≤ 10 なら：中点に段階 +1 の果物を正規サイズのボディで作り、初速は元の2個の速度の平均にする。得点を加算し、エフェクトを出す（6-1〜6-6）。
   - 段階 = 11 なら：新しい果物は作らない。+66 点とスイカの特別演出を出す。
   - 新しい果物の `spawnTime` を今のゲーム時間にする（ゲームオーバー判定の1秒の猶予に使う）。
4. キューを空にする。

### 8-4. ゲームオーバー

| 項目 | 仕様 |
|---|---|
| 対象 | `spawnTime`（投下された時刻、または合体で生まれた時刻）から **1000ms 以上** たった果物 |
| 越えている状態 | 対象の果物のうち1個でも、上端 `y − r` が `Y_DEAD = 40` より小さい（線より上にある） |
| 判定 | 「越えている状態」が **途切れずに 2000ms**（ゲーム時間）続いたらゲームオーバー。途中で一度でも状態が解けたら、タイマーを 0 に戻す |
| 警告 | 「越えている状態」の間、デッドラインを赤く点滅させる（5-5） |
| 判定のタイミング | 毎ステップの後（合体処理の後） |

### 8-5. リトライ（完全な初期化）

1. `Events.off(engine)` → `Composite.clear(engine.world, false)` → `Engine.clear(engine)` を順に行い、古いエンジンへの参照をすべて捨てる。
2. 物理ワールドを作る関数 `new PhysicsWorld()` で、エンジン・壁・イベントを作り直す。
3. 果物の一覧・合体キュー・エフェクトの配列・ゲームオーバーのタイマー・スコア・クールダウンを初期値に戻す。
4. 時間による処理は `setTimeout` を使わず、すべてゲーム時間か実時間のタイムスタンプで判定する（リトライ後に古いタイマーが残らないようにするため）。
5. 果物のスプライトキャッシュは作り直さずに使い回す（灰色版のキャッシュも残す）。
6. 「現在の果物」と「NEXT」を抽選し直して PLAYING に戻る。

## 9. 物理仕様（パラメータ逆算）

### 9-1. 方針

本家の動きを数値目標（要件 5-2(A)）とし、等加速度運動の式と Matter.js 0.19.0 の積分式から、パラメータの初期値を逆算する。最終的な値は、計測テスト（11-3）の結果を見て調整する。

### 9-2. Matter.js 0.19.0 の積分式（換算の根拠）

`Body.update(body, deltaTime)` の中身（0.19.0）は次のとおり。

- 重力：`Engine._bodiesApplyGravity` で `force.y += mass × gravity.y × gravity.scale`
- 速度の更新：`velocity = (position − positionPrev) × (1 − frictionAir × deltaTime / 16.667) + (force / mass) × deltaTime²`
- 位置の更新：`position += velocity`

ここで `deltaTime` はミリ秒、`velocity` は u/step。1ステップあたりの速度の増分は `gravity.y × gravity.scale × dt_ms²`（u/step²）になる。これを u/秒² に直すと：

```
a [u/秒²] = gravity.y × gravity.scale × dt_ms² × (1000 / dt_ms)²
          = gravity.y × gravity.scale × 1,000,000
```

**dt に関係なく、`a = gravity.scale × 10⁶`（gravity.y = 1 のとき）** となる。よって、

```
gravity.scale = PHYSICS.gravity [u/秒²] / 1,000,000
```

### 9-3. 重力の逆算

- 基準とする果物：段階3（ぶどう、r = 23）。投下位置の中心 y = −60 から、床に触れる位置の中心 y = 500 − 23 = 477 まで。**落下距離 h = 537u**。
- 目標の落下時間 t = 0.70秒（目標範囲 0.6〜0.8秒の中央）。
- 空気抵抗なしの場合：`g = 2h / t² = 2 × 537 / 0.49 ≈ 2192 u/秒²`
- 空気抵抗（frictionAir = 0.002）があると、速度に比例して減速する。線形の抵抗係数 `k = frictionAir × 60 = 0.12 /秒` のとき、落下距離は `x(t) = (g/k) × (t − (1 − e^(−kt))/k)`。
- **g = 2200 u/秒²** を採用：
  - 抵抗なし：t = 0.699秒
  - 抵抗あり（k = 0.12）：x(0.70) ≈ 524u なので、537u に届くのは約 0.708秒
  - 最大速度の制限（9-5、1400 u/秒）にかかるのは、落下の最後の約 0.1秒だけで、遅れは +0.01秒程度
  - **予測される落下時間は約 0.72秒**で、目標範囲 0.6〜0.8秒に入る。だんだん加速して落ちる（等加速度運動）。計測テストの実測値は 0.700秒（離散ステップのため、連続時間の式より少し早く着く）。
- `gravity.scale = 2200 / 10⁶ = 0.0022`（gravity.y = 1）。
- 物理はすべて論理座標（u）で計算し、画面の大きさは描画の倍率 s にしか影響しない。そのため、画面サイズを変えても落下時間や跳ね方は変わらない。

### 9-4. 反発（跳ね方）の逆算

- 反発係数 e で跳ね返ると、跳ねる高さは落下高さの e² 倍になる（空気抵抗を無視した場合）。
- 目標「落下高さの5〜10%」→ `e = √0.05 〜 √0.10 = 0.22〜0.32`。
- 理論値の初期案は 0.25（跳ねる高さ 6.25%）だったが、計測テストでは 4.5% にとどまった（Matter.js の位置補正と、着地ステップでのめり込みにより、理論値の約7割になる）。そこで **床・壁の反発 = 0.30** に変更した。計測値は 6.3〜7.0%（16章）。
- Matter.js 0.19.0 の静止判定の閾値 `Resolver._restingThresh = 2`（法線方向の相対速度が −2 u/step より遅い接触は、反発なしの静止接触として解く）があるため、2回目の跳ね返りはほとんど出ない。→ **1〜2回で収まる**。
- **果物同士の反発 = 0.12**。積み重なりで小刻みに跳ね続けないよう低めにし、「モチっと」受け止める感触を出す。

| `maxSpeed` | 1400（u/秒） | 独自処理：分割ステップごとに、速さがこれを超えていたら縮める | 1/60秒あたり 23.3u（分割ステップ1回あたり 7.8u）。最小の果物どうしの半径の和（24u）より小さく抑えると、果物同士がすり抜けず、めり込みの向きも逆にならない。空の床への着地速度（約1540 u/秒）を少しだけ抑える程度で、落下時間への影響は +0.01秒程度 |
| `maxAngularSpeed` | 20（rad/秒） | 独自処理：角速度の上限 | 小さい果物が合体の押し出しで異常に高速回転するのを防ぐ |
| `mergePushMaxSpeed` | 420（u/秒） | 独自処理（9-7） | 押し出された果物が跳ね上がる高さは最大で v²/2g = 420² / 4400 ≈ 40u。少し跳ねて連鎖が起きるが、吹き飛ばない |
| `mergePushDuration` | 200（ms） | 独自処理（9-7） | 正規サイズのボディの重なりが、位置補正で解消されるまでの時間（約12ステップ） |
| `massExponent` | 2.0 | 調整パネル専用（初期値では何もしない） | 質量 ∝ r^値。2.0 = 面積に比例（要件どおり）。比較実験用。積載テストは 2.0 のまま合格したので、質量比を緩める対策は使っていない |
| `substeps` | 3 | 1/60秒の1ステップの中で `Engine.update` を3回（1回 = 1/180秒）呼ぶ | 確認事項 Q10 の分割計算。値の調整（対策1）と反復回数の増加（対策2、最大60/40回）では積載テストのめり込みが6u以上残ったため採用。2分割でも合格したが、3分割（反復20/14回）は同じ処理時間でめり込みがより安定して小さかった（16章） |

### 9-6. 物理のボディ構成

**果物**
- 円を正多角形で近似する。Matter の `Bodies.circle` は小さい果物ほど辺の数が少なくなり（r = 12 だと12角形）、転がりがガタつく。そのため `Bodies.polygon` を使い、辺の数 n を半径から決める：r < 20 → 20、r < 45 → 28、r < 75 → 36、それ以上 → 44。
- 頂点の半径は `r / cos(π/n)` にする（外接多角形）。辺の中点がちょうど r になるので、見た目の円より内側に当たり判定が入り込まない（見た目が重なって見えない）。頂点での誤差は最大 1.3%（n = 20 のとき）。
- `label = "fruit"`、`plugin.fruit` に果物のデータ（段階・spawnTime・merging など）を持たせる。
- `restitution`・`friction`・`frictionStatic`・`frictionAir`・`slop` には、`PHYSICS` の果物用の値を入れる（ペアの実効値は、この節の後半の組み合わせ規則で決まる）。
- `enableSleeping = false`（眠ったボディは合体判定や押し出しに反応しにくくなるため）。

**壁と床**（静的ボディ、`label = "wall"`）

| ボディ | 中心 | 幅 × 高さ | 当たる面 |
|---|---|---|---|
| 床 | (200, 600) | 1000 × 200 | 上面 y = 500 |
| 左の壁 | (−100, −350) | 200 × 1900 | 右面 x = 0（y = −1300〜600） |
| 右の壁 | (500, −350) | 200 × 1900 | 左面 x = 400（y = −1300〜600） |

- 厚さ 200u は最大速度（23.3 u/step）の約8.5倍なので、高速でもすり抜けない。
- 壁は見た目の縁（y = 0）より 1300u 上まで続いている（見えない壁）。合体で押し出された果物が縁より上に跳ねても、コンテナの外へ落ちない（受け入れ基準13）。

**接触ごとに反発・摩擦を変える方法**（確認事項 Q5 の結論：`Pair.update` は差し替えない）
- Matter 0.19.0 は、ペアの値を毎ステップ `Pair.update` の中で両方のボディから計算し直す。決まり方は、反発 = 大きいほう、動摩擦 = 小さいほう、静止摩擦 = 大きいほう、slop = 大きいほう。
- 壁・床のボディには `restitutionWall`・`frictionWall`・`frictionStaticWall` を、果物のボディには `restitutionFruit`・`frictionFruit`・`frictionStaticFruit` を設定する。すると、ライブラリを書き換えずに次の実効値になる：

| ペア | 反発 | 動摩擦 | 静止摩擦 |
|---|---|---|---|
| 果物同士 | restitutionFruit = 0.12 | frictionFruit = 0.45 | frictionStaticFruit = 0.60 |
| 果物と壁・床 | max(0.30, 0.12) = **0.30** | min(0.20, 0.45) = **0.20** | max(0.50, 0.60) = 0.60 |

- 反発と動摩擦は、「壁の反発 ≥ 果物の反発」「壁の動摩擦 ≤ 果物の動摩擦」を守るかぎり、壁と果物で独立に決められる。静止摩擦だけは、果物と壁のペアが両者の大きいほうになる（初期値では 0.60）。挙動の要件はこれで満たせた（計測テスト・積載テストに合格）ので、差し替えは使っていない。
- 調整パネルには、いまの値から計算した実効値を表示する。

### 9-7. 合体時の押し出し

- 新しい果物は最初から正規サイズなので、周りの果物と重なった状態で生まれる。Matter の位置補正が重なりを解消するときに、周りの果物が押し出されて少し跳ねる（本家らしい連鎖のもと）。
- 吹き飛びすぎを防ぐため、合体のたびに「押し出しゾーン」を登録する：中心 = 新しい果物、継続時間 = `mergePushDuration`（200ms）。
- ゾーンが有効な間は毎ステップ後に、新しい果物と、その果物に触れている果物の速さを `mergePushMaxSpeed`（420 u/秒）以下に抑える（向きはそのまま）。
- 新しい果物の初速（元の2個の速度の平均）にも、同じ上限をかける。

### 9-8. 1ステップの処理順

1. `Engine.update(engine, 1000/60)`（この中で `collisionStart` / `collisionActive` が発生し、合体キューと接触数が記録される）
2. 合体キューを処理する（8-3）
3. 速さの制限（`maxSpeed`・`maxAngularSpeed`・押し出しゾーン）
4. 転がり抵抗（`rollingDamping`）
5. 安全策：果物の中心が x < −20、x > 420、y > 520 のどれかになったら、コンテナの中へ戻し速度を 0 にする（テストでは一度も働いていない。デバッグ表示の `rescue` で数える）
6. 壁・床への押し込み補正：果物が壁・床に `WALL_TOLERANCE`（0.5u）を超えてめり込んでいたら、接する位置まで戻し、壁に向かう速度成分を 0 にする（デバッグ表示の `wallfix` で数える）。合体で生まれた大きい果物が、隣の小さい果物を1ステップで壁へ押し込むことがあるため（最大20u）に追加した。壁と床は垂直・水平なので、戻す向きと量は正確に決まる
7. ゲームオーバー判定（8-4）
8. ゲーム時間を 16.667ms 進める

※ 1〜6 は1/60秒の中で `substeps`（3）回くり返す（合体・速度制限・補正も分割ステップごとに行う）。補間用の「1つ前の状態」は、1/60秒のステップの最初に保存する。

## 10. ゲームループと時間管理

### 10-1. 固定タイムステップ（アキュムレータ方式）

```
毎フレーム（requestAnimationFrame）:
  frameDt = min(今のタイムスタンプ − 前のタイムスタンプ, 250ms)
  accumulator += frameDt
  steps = 0
  while accumulator ≥ 16.667ms かつ steps < 5:
      物理を1ステップ進める（9-8）
      accumulator −= 16.667ms
      steps += 1
  if steps == 5 かつ accumulator ≥ 16.667ms:
      accumulator = 0   （処理落ちしたときは、追いつこうとせず遅れを捨てる）
  エフェクトを min(frameDt, 50ms) だけ進める
  描画する
```

- 1フレームの最大ステップ数は 5（83ms 分）。処理落ちしても暴走しない（スローモーションになるだけ）。
- 60Hz の画面ではほぼ毎フレーム1ステップ、120Hz の画面では2フレームに1ステップになる。物理の進み方はゲーム時間で決まるので、画面のリフレッシュレートで速さは変わらない。

### 10-2. 描画の補間

- `RENDER.interpolate`（初期値 **true**、確認事項 Q4 で採用）が true のとき、1つ前のステップと今のステップの、位置と角度を **同じ** `alpha = accumulator / 16.667` で線形補間して描く（角度は差を −π〜π に直してから補間）。表示する位置と角度は、常に同じ時点の補間状態になる。120Hz の画面でも動きがなめらかになる。
- false のときは、物理ボディの `position` と `angle` をそのまま描く（表示と物理が常にぴったり一致する）。
- どちらの場合も、見た目の回転は物理ボディの角度から決まる。描画のためだけに回転を加えることはしない。

### 10-3. 時間の使い分け

| 用途 | 使う時間 |
|---|---|
| 投下のクールダウン、ゲームオーバー判定、spawnTime、押し出しゾーン、オートプレイの投下タイミング | ゲーム時間 |
| エフェクト、UIのアニメーション、デッドラインの点滅、ゲームオーバー演出、オートプレイの無操作タイマー・移動 | 実時間（一時停止中は進めない） |
| BGM | 書き出したループを `AudioBufferSourceNode` で再生するので、JavaScript のタイマーは使わない（オーディオの時計だけで進む） |

### 10-4. タブの非表示

- `visibilitychange` で `document.hidden` になったら、`paused = true` にしてループを止める（`cancelAnimationFrame`）。
- 表示に戻ったら、前のタイムスタンプを捨て、`accumulator = 0` にしてからループを再開する。これで、非表示だった時間の分をまとめて計算して暴走することがない。
- ゲームは自動で再開する（非表示の間に物理もゲーム時間も進まないので、不利にならない）。プレイヤーが一時停止していた場合は、一時停止のまま戻る。
- 非表示の間は `AudioContext` も止める（7章）。

### 11-3. 計測テスト

- 条件：空のコンテナで、段階3（ぶどう）を (200, −60) から初速0で放す。参考として、段階1と段階5でも同じ測定をして表に並べる。
- 測定する値：

| 指標 | 定義 | 目標 |
|---|---|---|
| 落下時間 | 放してから、床との `collisionStart` が起きるまでのゲーム時間 | 0.60〜0.80秒 |
| 跳ね返りの割合 | 最初の接触から、次に下向きに動き出すまでの最高点を y_peak として、`(床で止まったときの中心 y(=500−r) − y_peak) / (500−r − (−60))` | 5〜10% |
| 跳ねた回数 | 床から 0.5u 以上離れた回数 | 1〜2回 |
| 止まるまでの時間 | 最初の接触から、「速さ < 3 u/秒 かつ 角速度 < 0.1 rad/秒」が 200ms 続いた状態に入った時刻まで | 1.5秒以内 |

- 結果は表で表示し、各指標に「測定値・目標範囲・差（範囲外ならどれだけ外れたか）・判定（OK／NG）」を出す。
- 結果は JSON でもコピーできるようにする。
- 本家の動画から測った値が後から渡された場合は、目標値を差し替えて、パラメータを調整し直す。

### 11-4. 積載テスト（受け入れ基準12の確認用）

- 専用の物理ワールド（合体は無効）で、床に小さい果物を3段に並べる（さくらんぼ16個＋15個、いちご11個、計42個）。1.5秒落ち着かせてから、その上にスイカ1個を落とし、30秒分（1800ステップ）を同期的に計算する。スイカを落とす x 位置はずらせる（`offsetX`）。
- 測定する値：
  - スイカの下にある小さい果物の数（5秒後と30秒後）
  - 果物同士の最大のめり込み量（2秒後以降の最大値と、30秒後の値。めり込み = 半径の和 − 中心間の距離）
  - 床への最大のめり込み量
  - スイカの中心の y の、5秒後（落ち着いた後）から30秒後までの変化量（沈み込み）
  - 小さい果物が床より下に出た数
- 合格の目安：スイカの下に10個以上、最大めり込み ≤ 2u（最小の果物の半径 12u の約17%）、30秒後のめり込み ≤ 1u、床より下 0個、沈み込み ≤ 1u。沈み込みが 1u を超えた場合は、「下の果物の数が減った（はじき出されて崩れた）」かつ「めり込みが残っていない」ときに限り、要件で許容される自然な崩れとして扱う。

## 12. レスポンシブ・入力・その他

### 12-1. 拡大縮小と高解像度

- `resize` と `orientationchange` のときに（100ms 間引き）：
  1. レイアウト（3-2）から、使える領域の大きさを求める
  2. `s = min(使える幅 / 460, 使える高さ / 660)`
  3. Canvas の CSS サイズ = (460s, 660s) px、実際のピクセル数 = CSS サイズ × `devicePixelRatio`（整数に丸める）
  4. 描画の変換 = `setTransform(s·dpr, 0, 0, s·dpr, 30·s·dpr, 130·s·dpr)`（論理座標の (−30, −130) を左上に合わせる）
  5. スプライトとコンテナのキャッシュを作り直す
- 物理の状態には一切触れない（表示だけが変わる）。
- `devicePixelRatio` の変化（ブラウザのズーム、別のモニターへの移動）は、`matchMedia("(resolution: Xdppx)")` の change で検知し、同じ処理をする。

### 12-2. スマホでのスクロールと拡大の防止

- `<meta name="viewport" content="width=device-width, initial-scale=1, maximum-scale=1, user-scalable=no, viewport-fit=cover">`
- `html, body { position: fixed; inset: 0; overflow: hidden; overscroll-behavior: none; touch-action: none; user-select: none; -webkit-user-select: none; -webkit-touch-callout: none; }`
- 高さは `100dvh` を使う（使えない環境では `100vh`）。
- `touchmove`・`gesturestart`・`dblclick` で `preventDefault()`（`passive: false`）。
- 入力は Pointer Events に統一し、`setPointerCapture` で、指がフィールドの外に出てもドラッグを続ける。

## 15. 確認事項

承認時の回答：Q1〜Q3・Q7〜Q9・Q11 は推奨案どおり。Q4 は補間ありを採用し、位置と角度を同じ補間係数でそろえる。Q5 は差し替えなしを先に試す（結論は 9-6）。Q6 と Q10 は、基準を満たせない場合に「値の調整 → 反復回数 → 分割計算 → 質量比」の順で自分で判断する（結果は 9-5 と 16章）。Q12 は実測値なし（仕様書の目標値で調整）。以下は承認前の記録。

| # | 内容 | 推奨案 |
|---|---|---|
| Q1 | **スイカ同士の合体**：両方消えて +66 点でよいか。代わりに、より大きな得点（例：+132）にする案もある | 要件どおり **+66**。最上位の段階の得点を1回分もらう、というほかの段階と同じ決まりで説明できる。演出はスイカ誕生と同等以上にする |
| Q2 | **出現確率**：段階1〜5 = 30:25:20:15:10 | この重みを推奨。均等（各20%）にすると、序盤に大きい果物が多く出て難しくなる |
| Q3 | **デッドラインの位置**：縁から 40u 下（内高の8%）。投下位置は縁から 60u 上 | 推奨。縁そのものに線を置くと、線が枠と重なって見づらく、余裕もなくなる |
| Q4 | **描画の補間**：120Hz の画面で動きをなめらかにするため、直前の2ステップの間を補間して描く。この場合、表示の角度は「2つの物理ステップの角度の間の値」になり、厳密には物理ボディの角度とその瞬間だけずれる | **補間あり**を推奨（60Hz の画面では実質的に差はない）。要件の「ぴったり一致」を厳密に守りたい場合は、補間なしを初期値にする（デバッグパネルでいつでも切り替えられる） |
| Q5 | **接触ごとの反発・摩擦**：Matter.js の `Pair.update` を差し替えて実現する（9-6）。ライブラリの内部関数を書き換える方法である | 推奨。バージョンを 0.19.0 に固定するので安全。予備の方法も用意する |
| Q6 | **大小の質量比**：密度を全段階で同じにすると、質量比は最大で約72倍になり、Matter.js では小さい果物が押しつぶされやすい。まず反復回数を増やして対応する。それでも受け入れ基準12を満たせなかった場合、質量を `r^1.6` 程度に比例させる（質量比を約30倍に抑える）案を検討したい | まず要件どおり（面積に比例）で実装し、積載テストの結果をフェーズ3で報告する。満たせなかった場合は、変更前に相談する |
| Q7 | **ゲームオーバー時の物理**：演出の開始と同時に物理演算を止める（果物を灰色にする間に果物が動かないように） | 止めるのを推奨 |
| Q8 | **着地音**：要件の効果音には含まれていない | 付けない（音が多すぎるのを避ける）。希望があれば、強い着地のときだけ鳴る小さな「コトッ」を追加する |
| Q9 | **スタート画面**：最初の操作で音声の解禁とゲーム開始を同時に行う、簡単なスタート画面をつける | つけるのを推奨（最初のクリックで、意図せず果物を落とすのも防げる） |
| Q10 | **物理の安定性の予備案**：60Hz の1ステップで不安定な場合、1フレームを 1/120秒×2回 の小さなステップに分ける案がある | 要件どおり 60Hz で実装する。積載テストで問題が出たときだけ相談する |
| Q11 | **進化の輪の到達表示**：そのゲームでまだ作っていない段階6以上を薄く表示する（要件にはない追加） | 追加を推奨（目標が見えて遊びやすい）。不要なら全種を同じ濃さで表示する |
| Q12 | **本家の動画から測った目標値**：計測テストの目標値（落下0.6〜0.8秒、跳ね5〜10%、停止1.5秒以内）を差し替える値があれば、承認時に一緒にお知らせください | 指定がなければ、要件の目安値で調整する |

| 2 | `tests/selfcheck.js` の R5 を、上記の動きを確認する内容に改めた | 手動に戻った後の放置（マウス30秒・キー15秒・タップ10秒）、開始5秒以内の操作、リトライでの再発動を確認する |

### v1.5（iPhone で BGM が途中から聞こえなくなる不具合の修正）

| # | 変更点 | 理由・内容 |
|---|---|---|
| 1 | BGM の再生方式を、「25ms ごとのタイマーで音を1つずつ予約する」方式から、「起動時に1ループを音声データへ書き出し、1つの再生ノードでループ再生する」方式に変えた（7-2）。曲・音色・音量は v1.3〜v1.4 と同じ | 旧方式は、8分音符ごとに新しい発音ノードを作り（1分で約2000個）、つないだままにしていた。iOS Safari は終わったノードの解放が遅く、溜まると音が止まることがある。またタイマーは、低電力モードなどで遅れると予約が抜ける。新方式は再生中にノードもタイマーも使わないので、どちらも起きない |
| 2 | BGM の見張りを追加した。再生ノードが消えていたら毎フレームの確認で鳴らし直す。iOS の `interrupted` 状態や画面復帰（`pageshow`・`focus`）でも再開を試みる | 通知音・着信・Siri などで iOS が音声を中断した後に、自動で戻らないことがあるため |
| 3 | 効果音のノードを、鳴り終わったら外す（`onended` で `disconnect`）ようにした | 長く遊んだときにノードが溜まらないようにするため（理由は1と同じ） |
| 4 | `tests/selfcheck.js` に R2b（26秒間鳴り続けること、止められても自動で復帰すること）を追加し、R2 を新しい再生方式に合わせた。R5 の「自動投下がないこと」の判定を、投下の回数を直接数える方法に直した | R5 は、合体が起きると数が合わなくなる判定式になっていたため |
